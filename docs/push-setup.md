# 后台推送配置指引

App 不在前台时，新来的外部来信怎么送到你手机上。

不配也能用 —— 只是 App 被系统冻结、或者被你划掉之后，那段时间的来信要等你下次打开 App 才会知道。**收信本身不受影响**，推送只是「快一步」。

---

## 一、整条链路长什么样

```
外部来信
  → 你的 cloud-mail 实例       （收到了这封信，触发 Webhook）
    → mail-push 中转 Worker    （把事件扇出到 FCM）
      → FCM / APNs             （Google / Apple 的推送通道）
        → 手机通知栏            （点一下直达那封信）
```

三个地方各有一份配置，**错一处就静默失败** —— 不会报错，只是通知不来：

| 谁 | 要做什么 | 拿什么做 |
|---|---|---|
| App（这台设备） | 填「中转地址 / 实例位 / 配对码」三条值，打开开关，登记设备 | 下面第二节 |
| 你的实例后台 | 打开 Webhook 推送，填地址与 secret | 下面第三节 |
| 中转 Worker | 部署一次，开一个实例位 | 下面第四节 |

`mail-push` 是**可以多人共用的**：一个中转端服务任意多个 cloud-mail 实例，每个实例一位。所以最常见的情况是「别人已经部署好了，你只需要两条值」——那就是第一节（普通用户）。

App 里对应的是 **设置 → 后台推送** —— 那是**七页的分步向导**（第 ① 页就是状态），逐页说明见本文第二章各步。本文是它的展开版。

> **向导怎么走。** 顶部七个圆点是进度（做过的打 ✓），底部是 `上一步 / 下一步`，**每一页的主动作长在正文里**（保存 / 开关 / 登记 / 检查），不跟导航钮混在一起。系统返回键 = 上一步。第 ① 页那三行状态是可点的，直接跳到对应的那一页 —— 配好的人不必连点五次「下一步」。
>
> 旧的深链 `/settings/push/guide` 仍然可用，现在它重定向到 `/settings/push`。

## 二、普通用户：四步

你手上有别人给你的三条值：**中转地址**、**实例位 id**、**配对码**。

向导的七页与这四步的对应关系：① 状态 → ② 三条值 → ③ 开关 → ④ 登记 → ⑤ 实例后台（本文第三节）→ ⑥ 检查 → ⑦ 说明与限制。

### 第 1 步 · 把三条值填进 App（向导第 ② 页）

第 ② 页上三个输入框：

- **中转地址**：形如 `https://push.example.com`，不含末尾斜杠也行（会归一化）。
- **实例位 id**：形如 `inst-a1b2c3`。
- **配对码**：形如 `ABCD-EFGH-JKLM-NPQR-STUV`，**区分大小写**。

填完点 **保存这三条值**。这一页底部那条说明是重点：**配对码没有任何地方能查** —— 它是中转位被创建的那一刻回显一次的值，之后连中转端的管理员也读不回来（接口里被 mask 成 `******`）。所以「我忘了」的正确答案是**找发给你的人重新生成一个**，不是去哪个页面翻。

> 它同时就是实例后台要填的 **webhook secret** —— 同一个值，两处用。
>
> 部署者不必手敲 curl：把这一页的「中转是我部署的」那一段展开，填管理口令，点 **一键开通**，它替你 `POST /admin/instances` 并把返回的实例位与配对码直接落盘。管理口令只作为请求头发出，不写 prefs、不进钥匙串、不写日志。

登记之后的中转端回执会直接显示在页面底部。**失败时看它回的是哪一句。** 中转端把两种失败分开了：说「配对码不正确」就是配对码的事（填错、或者被轮换过）；说「设备号格式不对」则与配对码无关 —— 那是设备号少了实例位前缀，正常由 App 自己补上，报到这句基本是客户端太旧。这两句以前合成一句，指错方向；现在它们各自指一条路。

### 第 2 步 · 打开「后台推送」总开关（向导第 ③ 页）

这一页**只有一个开关**，没有别的东西可点。它和「填了三条值」是两件不同的事：值填好了但开关关着 = **配置留着但不收推送**（手机省电、暂时不想被打扰时这么用）。启动时的自动登记也认这个开关。

关掉它**会顺手退订** —— 中转端那份注册会被删掉，不会留着在「我明明关了」的情况下继续推。

### 第 3 步 · 登记这台设备（向导第 ④ 页）

点 **登记这台设备**。三件事会一起发生：FCM 拿一个 token、把每个邮箱绑上去、中转端记下这台设备。**第一次点的时候系统会问通知权限** —— 就是这一步在问。

启动时 App 也会自己登记一遍（幂等），所以这一页主要是用来**确认**：下面「中转端记着的邮箱」应该列着你的邮箱。同一页还有一个 **退订**，它把本机在中转端的注册全删掉。

### 第 4 步 · 在实例后台打开 Webhook 推送（向导第 ⑤ 页）

**这一步只能在实例后台做**，也是所有人最容易漏的一步。见下一节。

向导第 ⑤ 页会问一句「这个 cloud-mail 实例是你在管吗？」—— 只决定要不要给你一段能直接转发的话，**两条值在两种答案下都照常显示**，所以这不是一个岔路。这个答案会记住（换一次答一次，不用每次重答）。

因为这一步发生在**另一个网站**上，App 看不到你做没做，所以第 ⑤ 页底下有一个勾：**「我已经在实例后台填好了」**。勾上它就记住「这一步做完了」（记的是**当时那三条值**：地址或配对码一改，这个勾会自己取消 —— 那种情况下确实得回实例后台重填一遍）。另外，只要中转端真的收到过你实例的一封 webhook，这一页也会直接算完成，连勾都不用 —— 那是唯一一条不靠自述的客观证据。

## 三、实例管理员：多做的两件事

你有一台自己的 cloud-mail 实例（换句话说是你自己能登进 `/sys-setting`）。

### 1. 把两条值填进实例后台

实例后台 → 系统设置 → **Webhook 推送**：

- `webhookUrl`：`https://<中转地址>/<实例位 id>/webhook`。**末尾的 `/<实例位>/webhook` 不能少** —— 向导第 ⑥ 页那次检查抓的就是这一条。
- `webhookSecret`：就是那个配对码。
- **把那一栏的开关拨开。**

### 2. 把三条值发给要用推送的人

中转地址、实例位 id、配对码。配对码是「谁都能收这个实例的通知」的凭证，**发的时候走个私密渠道**（发给一个人就开一个位，别多人共用一个）。

### 两个踩过的坑

**坑一：开关的取值是反的。** 实例后台那一栏的开关在数据库里叫 `webhookStatus`，**`0` 才是「启用」**（`webhookStatus === 0 ? enabled : disabled`）。字段名和直觉相反，所以「地址填对了、secret 也填对了，就是收不到」的第一嫌疑永远是这一栏没拨开。

**坑二：地址填了 `http://` 不会被升级成 `https://`。** 实例后台保存前会过一遍 `toOssDomain()`：**不以** `http` 开头的补上 `https://`，以 `http` 开头的则原样留下（只顺手去掉尾斜杠）。也就是说 `http://` 会真被存成 `http://`，而中转端是 HTTPS 的 —— 那一条永远连不上。所以要么直接填 `push.example.com`，要么填完整且正确的 `https://…`。

**坑三：IP 地址填不进去。** 实例后台保存时会拦一道 `isIpUrl()`，形如 `http://1.2.3.4/...` 的地址会被直接拒绝（要域名）。中转端 Worker 本来也走 Cloudflare 的边缘域名，所以这一条在实践中不成问题。

### 检查（向导第 ⑥ 页）

「后台推送」向导的第 ⑥ 页只有一个按钮：**检查这条链路**。它一次问清四件事，并把结论逐条列在按钮下面：

- **中转连不连得上**（`/health`）；
- **中转端有没有配 FCM 服务账号**（`fcmConfigured` —— 没有它，前面全对也投不出去）；
- **配对码对不对**（`secretOk`；不对就是它被别人轮换过，要一个新的）；
- **地址的路径对不对**（`urlOk` —— 抓的就是上面那个「少了尾巴」）；
- **这个位到底有没有真的收到过信**（`lastEventAt`）。

前四条全过但 `lastEventAt` 是空的，说明**中转端从没收到过你实例的 webhook** —— 那就是上面两个坑之一，或者开关没开。这一条比前几条有用得多：它是整条链路唯一一次「真的发生过」的证据。

**通过之后这次结论会被记住**（存在钥匙串里，绑定当时那三条值）：下次再进配置页，第 ⑥ 页会显示「上次是什么时候检查通过的」，进度条上那一步也直接算完成 —— 不用为了看一眼状态重新点一次检查。反过来，改了地址或配对码，这份记录就作废（它证明的是**改之前**那套值能通）。

> 以前这是两个按钮（「测试连接」与「自检」），问的其实是同一条链路上相邻的两段，用户得先猜哪个先点、再猜哪个的失败更严重。合成一个之后「哪一条不对」由页面直接指出来。

## 四、中转部署者 / 从零搭一套

### 部署 mail-push

```bash
cd mail-push
npm install
npx wrangler login

# 1. 建库，把返回的 uuid 填进 wrangler.toml 的 database_id
npx wrangler d1 create mail-push
npx wrangler d1 execute mail-push --remote --file=./schema.sql

# 2. 管理口令（不写进仓库）
npx wrangler secret put ADMIN_TOKEN

# 3. FCM 服务账号（Firebase 控制台 → 项目设置 → 服务账号 → 生成新的私钥）
npx wrangler secret put FCM_SERVICE_ACCOUNT   # 整串 JSON
npx wrangler deploy
```

> **坑：`[vars]` 里不能有与 secret 同名的变量。** 变量和密钥共用同一个命名空间，`[vars]` 里留一个 `ADMIN_TOKEN = ""` 会让 `wrangler secret put ADMIN_TOKEN` 直接失败（`Binding name 'ADMIN_TOKEN' already in use`）。两个都必须从 `[vars]` 里拿掉。拿掉之后 `env.X` 就是 `undefined`，所以中转端所有 env 读取都走 `envStr()`。

### 建 Firebase 项目

中转端通过 FCM 投递，需要一个 Firebase 项目的服务账号 JSON（上面第 3 步）。同时**把 App 的包名登记进去**，否则手机上收不到：

- Android：包名 `com.zenkee.mailapp`
- iOS / macOS：bundle id `com.zenkee.mailapp`

按你的构建方式把 `google-services.json` / `GoogleService-Info.plist` 放进对应目录。没有配置文件时 App 里会明说「这份构建里没有 Firebase 配置」，而不是让你配完一整套才发现收不到。

### 开一个实例位

部署完之后**不用手敲 curl** —— App 向导第 ② 页有一段 **一键开通（部署者）**（展开「中转是我部署的 —— 现开一个实例位」）：填管理口令，它替你 `POST /admin/instances`，把返回的实例位与配对码直接落盘。管理口令只作为请求头发出，不写 prefs、不进钥匙串、不写日志。

手敲的话是：

```bash
curl -s -X POST https://push.example.com/admin/instances \
  -H "Authorization: <ADMIN_TOKEN>" -H 'Content-Type: application/json' \
  -d '{"name":"我的实例"}' | jq
```

返回里的两样东西**只有这一次能拿到**：

```json
{ "code": 200,
  "data": { "instanceId": "inst-a1b2c3",
            "webhookSecret": "ABCD-EFGH-JKLM-NPQR-STUV",
            "webhookPath": "/inst-a1b2c3/webhook" } }
```

## 五、五条限制（值得提前知道）

1. **只覆盖外部来信。** 站内互发、发信、已读、删除都不触发推送 —— 那些只能靠 App 轮询。
2. **实例若是「规则收信」模式，webhook 完全不触发**（在推送之前就 return 了）。
3. **推送里只有元数据**（发件人 / 主题 / 验证码），没有正文。App 收到之后自己带 token 去实例拉正文 —— 所以转发一份正文也不会滞留在中转端。
4. **中转端能看到所有实例来信的元数据。** 自建的话就是你自己；用别人的中转端时这条要心里有数。
5. **App 被完全退出之后不触发同步。** 推送能叫醒的只有「进程还活着、只是不在前台」的 App（窗口关掉、被别的 App 盖住、最小化都算）。macOS 上 App 整个退出后，收到一条普通推送系统只把横幅画出来，**不会为了它启动进程** —— 点开横幅才会启动。所以那段时间的来信，要等你把 App 打开。这是平台限制，不是配置能改的。

## 六、常见故障对照表

| 症状 | 多半是 | 怎么办 |
|---|---|---|
| 登记时报「配对码不正确」 | 配对码填错 / 被轮换过 | 找发给你的人要一个新的；或先去第 ⑥ 页检查一遍 |
| 登记时报「设备号格式不对」 | 设备号少了 `<实例位>-` 前缀 | 正常情况下 App 自己会补（第 ① 页「高级」里能看到完整形态）；还在报的话是客户端太旧，升级即可 |
| 配置全对，但一封信都不推 | 实例后台那一栏开关没拨开 | 见第三节坑一（`webhookStatus = 0` 才是开） |
| 检查说地址不对（`urlOk: false`） | 地址末尾少了 `/<实例位>/webhook` | 按第 ⑤ 页给的完整地址重填 |
| 检查全过，`lastEventAt` 一直是空 | 中转端从没收到过 webhook | 检查实例后台的开关与地址；实例是「规则收信」模式也不触发 |
| 通知点进去落在邮件列表，不是那封信 | 推送来自**别的实例位**，或本机认不出这封信属于哪个实例 | 检查是不是换过实例位；换位时 App 会自动退订旧的 |
| Android 上 App 被杀之后要等十几分钟 | 那是**兜底轮询**（WorkManager 硬下限 15 分钟），不是推送 | 推送没配好时它就长这样；配好之后是秒级 |
| 这台设备一直收不到，别的设备正常 | FCM token 过期（重装 / 清数据 / 久未上线） | 向导第 ④ 页点一次「登记这台设备」重新上报 |
| 关掉开关之后还会收到通知 | 收到的是**本地通知**（App 活着时的轮询结果），不是推送 | 「后台推送」只管 App 不在时那一条路 |

## 七、隐私

中转端存的是**最小元数据**：`emailId`、发件人、主题、验证码码值，以及这台设备订阅了哪些邮箱。**刻意不存正文** —— webhook 的 body 里带着完整正文，多存一份等于把用户所有邮件的副本留在一个跟邮件系统无关的地方。

自建中转端的话，这些元数据在你自己手里。用别人的中转端，就等于让那个人看到你所有外部来信的**信封**（看不见信纸）。

设备号（向导第 ① 页「高级」里那个）是中转端认这台设备的依据，形如 `inst-a1b2c3-<32 位十六进制>`；前面那一段是实例位，作用是不让两个实例上号码相同的设备互相覆盖。它由 App 自动生成，不需要你改。
